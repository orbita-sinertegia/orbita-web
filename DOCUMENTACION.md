## Correcciones de seguridad del 22 de octubre de 2026 (rama fix/seguridad)

**Orden de publicación:** ejecutar `sql/2026-10-22_seguridad.sql` en el SQL Editor de Supabase y publicar esta rama inmediatamente después. Las pantallas de registro anteriores no funcionan con las políticas nuevas, y las nuevas necesitan las funciones de la migración. La migración no borra datos y se puede correr más de una vez.

- **Invitaciones de equipo:** solo administradores activos leen, crean, editan o borran `team_invitations`. La persona invitada consulta únicamente su invitación con `get_team_invitation(id)`. El registro llama a `accept_team_invitation`, que valida que la invitación no esté usada y que el correo de la sesión coincida, crea el perfil con el rol y departamento de la invitación, aplica sus permisos y la marca como usada en una sola transacción. El navegador ya no envía el rol.
- **Invitaciones de clientes:** `accept_client_invitation` crea el perfil siempre con rol `client`, vincula el cliente de la invitación, aplica permisos y la marca como usada. Si la invitación tiene correo, debe coincidir con el de la sesión (sin distinguir mayúsculas). La lectura de `client_invitations` no cambió.
- **Alta en Supabase Auth:** el registro está abierto y la confirmación de correo está apagada (`mailer_autoconfirm = true` al 22 oct 2026). Sin importar cómo se llame el trigger de alta ni si lee `raw_user_meta_data`, todo perfil creado fuera de `accept_*_invitation` nace como `client`, sin superadmin ni departamento. Las funciones de invitación activan `app.profile_from_invitation` solo durante su transacción. Para crear un perfil a mano desde el SQL Editor, crearlo y después actualizar su rol, o ejecutar antes `select set_config('app.profile_from_invitation', 'on', true)` en la misma transacción.
- **Licencia:** `app_license` sigue siendo de lectura para todos; solo el superadministrador puede editarla (igual que en la interfaz).
- **Perfiles:** el trigger `protect_user_access_fields` impide que desde la app (roles `authenticated`/`anon`) se cree un perfil directamente o se cambie `role` o `is_super_admin`. Reactivar una cuenta o cambiar el departamento queda solo para administradores, porque el departamento `lider` da acceso total. Las funciones security definer (`set_user_access_role`, `accept_*_invitation`) siguen funcionando.
- **Subtareas:** las crean, editan y borran administradores, el departamento Líder (`has_full_task_access`) y el responsable o creador de la tarea (`can_edit_task_items`).
- **Tiempo registrado:** cada quien registra solo su propio tiempo y edita o borra el suyo o el de tareas a su cargo. Administradores y Líder pueden todo. La lectura no cambió.
- **Revisor de ortografía (`api/check-spelling.ts`):** exige un JWT válido de Supabase (se valida contra `/auth/v1/user`) y responde 401 sin sesión. Solo visita URLs http/https públicas: bloquea direcciones locales, privadas y de metadatos, también tras redirecciones. Necesita `SUPABASE_URL`/`SUPABASE_ANON_KEY` o las `VITE_` equivalentes en las variables de entorno de Vercel.
- **Pendiente (otra rama):** los archivos subidos (`chat-files`, entregables) se guardan como URL pública permanente. Pasarlos a URLs firmadas requiere volver privado el bucket y migrar los links guardados.
- **Verificación:** `npm test` (32 pruebas), `npm run build` y 51 comprobaciones de la migración en PostgreSQL embebido (PGlite) con datos ficticios: invitaciones, cambio de rol y departamento, alta en Auth con metadatos maliciosos, licencia, subtareas, tiempo y Líder. La tabla `users` y el trigger de alta de Supabase Auth no están en el repositorio, así que hay que revisar el esquema real antes de activar la migración.

## 1. ¿Qué es esto?

Una app web de gestión de proyectos para la agencia: el equipo crea/avanza tareas, los traffickers/líderes las revisan y autorizan, y los clientes ven sus entregables y piden cambios. Todo corre sobre:

| Pieza | Para qué |
|---|---|
| **React + TypeScript** | La interfaz (todo lo que se ve y se hace clic) |
| **Vite** | Levanta el proyecto en desarrollo y lo compila para producción |
| **Tailwind CSS** | Estilos (clases como `bg-blue-600`, `rounded-xl`, etc.) |
| **Supabase** | Base de datos (Postgres), login de usuarios, archivos (storage) y tiempo real (chat/notificaciones) |
| **Vercel** | Donde vive la página publicada (sinertegia-launch-57) |
| **GitHub** | Donde vive el código (`tonytrafficker57/Sinertegia-proyector`). Cada `git push` a `main` redeploya solo en Vercel |

## 2. Cómo encenderlo en tu computadora

```bash
npm install        # solo la primera vez, o si cambia package.json
npm run dev         # levanta el servidor de desarrollo
```

Abre `http://localhost:5173`. Cada vez que guardas un archivo (Ctrl+S), el navegador se actualiza solo (hot reload) — no hace falta recargar a mano.

Para ver cómo quedaría en producción antes de subirlo:
```bash
npm run build       # compila a la carpeta dist/
npm run preview     # sirve esa carpeta compilada
```

**Si `npm run dev` o `npm run build` truenan** con un error de `rolldown-binding` o "Cannot find native binding": borra las carpetas `node_modules` y el archivo `package-lock.json`, y corre `npm install` de nuevo en tu máquina (es un problema de instalación, no del código).

## 3. Cómo se conecta a Supabase

Archivo [`src/lib/supabase.ts`](src/lib/supabase.ts): crea un único cliente de Supabase usando dos variables de entorno del archivo `.env` (que NO se sube a GitHub, está en `.gitignore`):

```
VITE_SUPABASE_URL=...
VITE_SUPABASE_ANON_KEY=...
```

Todo el resto del código importa ese cliente (`import { supabase } from '../../lib/supabase'`) y lo usa para:
- `supabase.from('tabla').select()/.insert()/.update()/.delete()` → leer/escribir en la base de datos
- `supabase.auth.*` → login, registro, recuperar contraseña, Google
- `supabase.storage.*` → subir archivos (fotos de chat, portadas de cliente)
- `supabase.channel(...)` → tiempo real (mensajes nuevos, notificaciones, quién está en línea)

En producción (Vercel), estas mismas variables se configuran en **Vercel → tu proyecto → Settings → Environment Variables** (ya están puestas).

## 4. Cómo entra cada usuario (autenticación)

[`src/contexts/AuthContext.tsx`](src/contexts/AuthContext.tsx) — el "cerebro" de la sesión. Se encarga de:
- Revisar si hay una sesión activa al abrir la app
- Buscar al usuario en la tabla `users` (por su `id`) para saber su **rol** (`admin`, `team`, `client`)
- Si alguien entra con Google pero su correo no está en la tabla `users`, lo rechaza (`unauthorizedEmail`)

[`src/App.tsx`](src/App.tsx) — decide qué pantalla mostrar según el estado de sesión:
- Sin sesión → [`LoginPage`](src/components/auth/LoginPage.tsx) (correo/contraseña, "olvidé contraseña", o Google)
- Recuperando contraseña → [`ResetPasswordPage`](src/components/auth/ResetPasswordPage.tsx)
- `user.role === 'admin'` → [`AdminDashboard`](src/components/admin/AdminDashboard.tsx)
- `user.role === 'team'` → [`TeamDashboard`](src/components/team/TeamDashboard.tsx)
- `user.role === 'client'` → [`ClientPortal`](src/components/client/ClientPortal.tsx)

## 4.1 ¿Cómo sabe la app si eres cliente, equipo o admin?

El login es **el mismo formulario para todos** (correo/contraseña o Google) — no hay manera de "elegir" el tipo de cuenta al entrar. Lo que decide qué pantalla ves es la columna `role` de la tabla `users` en Supabase, asignada desde que se creó la cuenta:

- **Cliente** → se pone solo (`role: 'client'`) cuando el cliente completa su registro desde el link de invitación que genera el admin al crear un proyecto ([`ClientRegistrationPage.tsx`](src/components/auth/ClientRegistrationPage.tsx)).

- **Equipo / Admin** → no hay botón en la app para esto. Se crea **a mano en Supabase** → Table Editor → tabla `users`, escribiendo `role` (`team` o `admin`) y `department`.

Con base en ese `role`, [`App.tsx`](src/App.tsx) decide qué dashboard mostrar.

## 6. Las funciones/flujos más importantes

**Flujo de una tarea** (todo en [`TaskDetailModal.tsx`](src/components/team/TaskDetailModal.tsx)):
1. Equipo trabaja la tarea → agrega links (opcional) → "Solicitar revisión"
2. Revisor aprueba → pasa a Trafficker, o pide retrabajo
3. Trafficker/Admin autoriza → el cliente ya la puede ver
4. Admin puede "Reactivar" una tarea en cualquier punto si algo salió mal

**Notificaciones**: cada acción importante (revisión solicitada, mensaje de chat, cambios pedidos por cliente, etc.) inserta una fila en la tabla `notifications`. [`NotificationBell.tsx`](src/components/shared/NotificationBell.tsx) las escucha en tiempo real con `supabase.channel(...)` y las muestra en la campanita del navbar.

**Chat**: [`TeamChat.tsx`](src/components/chat/TeamChat.tsx) (equipo) y [`ClientChatRoom.tsx`](src/components/chat/ClientChatRoom.tsx)/[`ClientChatsHub.tsx`](src/components/chat/ClientChatsHub.tsx) (por cliente). Los mensajes se guardan en `chat_messages` y se reciben en vivo por canal de Supabase; al mandar un mensaje se notifica a los demás miembros.

**Login con Google**: botón en [`LoginPage.tsx`](src/components/auth/LoginPage.tsx) llama a `supabase.auth.signInWithOAuth({ provider: 'google' })`. Está configurado en tres lugares externos (si algún día deja de funcionar, revisa ahí primero):
- Google Cloud Console → proyecto "Clienes Ads Sinertegia" → Auth Platform → Clientes → "Sinertegia Login"
- Supabase → Authentication → Providers → Google (switch debe estar **activado**)
- El "Callback URL" de Supabase debe coincidir con el "URI de redireccionamiento autorizado" en Google Cloud

## 8. Bitácora de cambios

- **Modal de entrega simplificado**: el flujo principal ahora prioriza fecha, entregables, revisor y el botón “Enviar a revisión”. Dependencias, subtareas y tiempo trabajado se agruparon bajo “Opciones adicionales”; comentarios se muestran en una sección desplegable con contador. El indicador de tres pasos se reemplazó por una línea compacta, se eliminó el botón “Cerrar” duplicado y el nombre del link pasó a ser opcional (se genera desde el dominio). La advertencia de entregable obligatorio aparece solo cuando se intenta enviar sin adjuntar nada.
- **“Por autorizar” abre la tarea exacta**: al pulsar la fila “Por autorizar” de la bandeja “Requiere atención”, ya no se abre la vista general del proyecto. Se abre directamente el modal de la tarea pendiente correspondiente, con un aviso azul que repite el nombre exacto y señala “Tarea que debes autorizar”. El botón “Ir a la decisión” desplaza al administrador hacia la sección de autorización o solicitud de cambios, que también queda resaltada.
- **Reloj limitado al turno diario**: se corrigió la recuperación que podía mostrar más de 24 horas al tomar una sesión abierta del día anterior. El reloj solo recupera sesiones iniciadas en la fecha local actual y usa `work_start`/`work_end` de cada integrante (con 9:00–18:00 como respaldo). Las sesiones antiguas que hayan quedado abiertas se cierran automáticamente a la hora de salida configurada. Si el error previo creó varias entradas del mismo día, se conserva la primera para respetar la hora real de inicio y al marcar salida se cierran todos los duplicados del día.
- **Bandeja “Requiere atención” simplificada**: las categorías con contador `0` ahora se ocultan automáticamente, por lo que la tarjeta solo muestra pendientes reales y reduce su altura según el contenido. Si autorizaciones, vencimientos y cambios están todos en cero, se muestra un único estado compacto “Todo al día”. La lógica de las tres categorías se conserva; únicamente cambia su presentación.
- **Corrección del reloj al refrescar**: `WorkSessionContext.tsx` ahora recupera la sesión laboral abierta más reciente usando `ended_at IS NULL`, sin depender de una fecha UTC ni fallar si quedaron varias filas abiertas. El contador se reconstruye desde `started_at`, por lo que conserva el tiempo trabajado después de refrescar. Antes de crear una entrada nueva, `checkIn()` vuelve a buscar una sesión abierta para evitar duplicados. Las fechas nuevas se guardan con la fecha local del dispositivo y un fallo temporal de Supabase ya no abre erróneamente el modal de entrada.
- **Panel principal más visual y accionable**: la vista inicial del administrador ahora incluye un “Resumen ejecutivo” con proyectos activos, tareas abiertas, tareas terminadas en los últimos 7 días y personas activas. Se añadió un indicador de salud operativa calculado según proyectos activos sin tareas vencidas, y una bandeja permanente “Requiere atención” para autorizaciones, tareas fuera de fecha y cambios solicitados por clientes. Las tarjetas navegan a las vistas ya existentes y muestran estados vacíos claros cuando todo está al día. El diseño se adapta a tablet y móvil.
- **Optimización de carga sin eliminar funciones**: los dashboards de Admin, Equipo y Cliente ahora se cargan de forma diferida desde `App.tsx`. La animación WebGL de `FloatingLines` conserva todos sus efectos, pero Three.js se descarga solo al mostrar el login. La generación de reportes conserva `html2canvas` y `jsPDF`, pero esas librerías se descargan únicamente cuando el usuario pulsa “Generar PDF”. El paquete inicial de producción bajó de aproximadamente 2.2 MB a 430 KB; las funciones pesadas quedaron en módulos independientes. También se añadió `AppErrorBoundary.tsx`, que reemplaza una pantalla blanca por un mensaje recuperable con botón para recargar si ocurre un error no controlado.

- **5 funciones nuevas en la tarea** ([`TaskDetailModal.tsx`](src/components/team/TaskDetailModal.tsx)), todas en el SQL [`sql/2026-07-15_subtareas_tiempo_dependencias_recordatorios.sql`](sql/2026-07-15_subtareas_tiempo_dependencias_recordatorios.sql):
  1. **Adjuntar archivos reales**: `uploadFile()` (antes `uploadHtmlFile()`) ya no restringe a `.html` — acepta cualquier archivo hasta 20MB (imágenes, PDF, Word, etc.), sube al mismo bucket `chat-files` bajo `task-deliverables/{task_id}/...`, y `fileIconFor()` elige el ícono según la extensión (imagen/PDF-Word/html/link).

## Misiones sin fecha — ventana después del check-in (23 de octubre de 2026, rama feat/fechas-misiones)

De 242 tareas activas, casi ninguna tenía `commitment_date`. Esta ventana hace que cada integrante del equipo le ponga fecha a sus propias misiones justo después de checar entrada, en vez de esperar a que un admin se las asigne.

- **Quién la ve:** solo `role === 'team'`. Administradores (incluido super admin) y clientes nunca la ven.
- **Cuándo aparece:** después de que la persona tiene sesión abierta hoy (`currentSession` del checador) y el `CheckInModal`/su aviso de confirmación ya se cerraron. No se encima con el checador ni con `OvertimeModal` — si cualquiera de esos dos vuelve a abrirse, la ventana se oculta hasta que se liberen. Si la persona ya había checado y recarga la app, vuelve a salir mientras no la haya saltado hoy y queden misiones sin fecha.
- **Qué cuenta como "misión sin fecha"** (`src/lib/missingDates.ts → isUndatedMission`): tarea asignada a la persona, sin `commitment_date`, que no esté realmente terminada (reutiliza `isTaskDone` de `roadmapPhases.ts`, así que una tarea en revisión o con cambios solicitados sigue contando), que no sea del departamento `cliente`, y cuyo proyecto no esté `completado`.
- **Orden** (`orderMissions`): primero el proyecto con fecha de lanzamiento más próxima (se usa como proxy de "más avanzado/activo" — un proyecto cerca de lanzar está más adelante en el embudo que uno sin fecha aún); los proyectos sin fecha de lanzamiento van después, ordenados por actividad más reciente (`updated_at` máximo entre sus misiones). Dentro de cada proyecto, por fase del embudo (`PHASES`) y luego por fecha de creación — no existe un campo `position` en `tasks`, así que la fecha de creación es el proxy del orden de la plantilla.
- **Guardar:** botón "Guardar" por fila y "Guardar todas" (solo las filas con fecha elegida). El update reutiliza el mismo patrón que ya usa `TaskDetailModal.saveCommitDate` (`update(...).eq('id', id).eq('assigned_to', user.id).is('commitment_date', null).select('id')`); si no regresa filas, se muestra un error en esa fila y no se quita de la lista. Cuando ya no queda ninguna misión, se muestra "¡Listo! Todas tus misiones tienen fecha ✅" con un botón para continuar.
- **Saltar:** "Lo hago después" (o cerrar con la X o Escape, que cuenta igual) guarda `localStorage['misiones-sin-fecha:skip:<userId>'] = <fecha CDMX de hoy>`. Al día siguiente vuelve a salir.
- **Validaciones:** no se permiten fechas pasadas (comparadas contra la fecha CDMX de hoy, `min` del input y revalidado al guardar). Si la fecha elegida queda después de `project.launch_date`, se muestra un aviso ámbar ("Queda después del lanzamiento") pero se permite guardar.
- **Contador para admin:** en **Operación → Tareas del equipo** (`TeamTasksManager.tsx`), cada integrante en la barra lateral muestra "Sin fecha: N" en ámbar (o "Al día ✅" en verde si N = 0), y arriba hay un total "X sin fecha en el equipo". Se eligió esta vista (y no "Carga del equipo") porque ya recibe `tasks` completo con el proyecto embebido, sin necesitar una consulta adicional.
- **Sin cambios de base de datos:** el equipo ya puede actualizar `commitment_date` de sus propias tareas (mismo patrón que `TaskDetailModal`). `sql/2026-10-23_fechas_misiones_revision.sql` es de solo lectura, para confirmar en Supabase que las políticas de `tasks` en efecto lo permiten (y no hay un trigger bloqueándolo).
- **Decisión propia:** se interpretó "proyectos terminados" como `project.status === 'completado'` (el único estado de cierre que existe hoy en `projects.status`; no existen `archivado`/`cancelado`).
- **Fase 2 (no implementada)**: verificación de "Oficina" por IP pública del Wi-Fi; pausas de comida y justificantes (vacaciones, permiso, incapacidad) para que no cuenten como `sin_registro`; resumen diario por correo/WhatsApp y reporte semanal en PDF; aviso de inactividad dentro de la app ("¿Sigues trabajando?").

## Editar y archivar tareas (administradores) (23 de octubre de 2026, rama feat/admin-editar-archivar)

Antes, un administrador solo podía completar o **borrar para siempre** una tarea del equipo (`admin_delete_team_task` eliminaba todo de inmediato: comentarios, entregables, subtareas, tiempos y calificaciones). Ahora puede **editar** cualquier campo y **"eliminar" de forma recuperable (archivar)**; el borrado definitivo queda como una acción excepcional, solo disponible desde Archivadas y únicamente sobre tareas ya archivadas.

- **Quién puede:** administradores activos: `role === 'admin'` o `is_super_admin` (mismo criterio que `is_active_admin()` en SQL, que es lo que validan las funciones en el servidor). Los botones de editar/archivar no aparecen para equipo ni clientes, y aunque alguien llamara las funciones directo, el servidor las rechaza.
- **Dónde están los botones:**
  - **Operación → Tareas del equipo** (`TeamTasksManager.tsx`): ícono de lápiz (editar) y archivo (archivar) en la tabla y en las tarjetas móviles; pestaña **"Activas" / "Archivadas (N)"** para alternar entre la lista normal y las tareas archivadas.
  - **Detalle de proyecto** (`ProjectDetail.tsx`): columna "Acciones" en la tabla de tareas del proyecto (solo visible para admin).
  - **Detalle de una tarea** (`TaskDetailModal.tsx`): ícono de lápiz y de archivo junto al selector de estatus, en la cabecera.
- **Editar** (`EditTaskModal.tsx` + `admin_update_task`): reutiliza los campos y estilos de `CreateTaskModal` — título, descripción, proyecto, responsable, departamento, prioridad, fase de la hoja de ruta, fecha de inicio, "La necesito para", fecha de entrega, quiénes revisan y autorizan, y de qué tarea depende. Si el departamento es `cliente`, el responsable se fija automáticamente al usuario cliente del proyecto (mismo candado que ya aplica el trigger `enforce_client_task_assignment`). Solo se envían al servidor los campos que realmente cambiaron (`src/lib/adminTasks.ts → buildTaskChanges`); si no hay cambios, se muestra "No hay cambios" sin llamar a Supabase. `admin_update_task` aplica solo las llaves enviadas con `jsonb_populate_record` (convierte cada valor al tipo real de la columna), mantiene `approver_id` igual al primer elemento de `approver_ids`, y rechaza dependencias de la tarea consigo misma o circulares directas. Las tareas del departamento cliente no exigen revisor.
- **Archivar / restaurar** (`ArchiveTaskModal.tsx` + `admin_archive_task` / `admin_restore_task`): archivar pide un motivo opcional y mueve la tarea a "Archivadas"; desde ahí se puede "Restaurar" (vuelve a aparecer en todas las vistas normales) o "Borrar definitivamente".
